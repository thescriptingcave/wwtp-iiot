# 02-01 — CTEs: naming the steps

**Previous:** [README](README.md) · **Next:** [02-02](02-02_joins.md)

A query about a plant tends to grow in the same way every time: a filter, then an
aggregate, then a filter *on the aggregate*, then a comparison against yesterday,
then a `LIMIT`. By the fifth step you have a `FROM` clause containing three
subqueries and a `WHERE` clause that has to be read inside out.

A **common table expression** gives each step a name.

## The question

> Which signals are behaving badly today compared with their own normal band —
> and were they behaving badly yesterday too?

Three things, and the third one is a comparison against a different time window,
which is where a nested subquery stops being readable.

## The nested version, which is what you would otherwise write

<!-- check: skip -->
```sql
SELECT
    t.signal_id,
    t.today_mean,
    t.yesterday_mean,
    round((t.today_mean - t.yesterday_mean)::numeric, 3) AS change
FROM (
    SELECT
        s.id AS signal_id,
        avg(CASE WHEN r.ts >= :today THEN r.value END)        AS today_mean,
        avg(CASE WHEN r.ts <  :today THEN r.value END)        AS yesterday_mean
    FROM reading r
    JOIN signal s ON s.id = r.signal_id
    WHERE r.ts >= :yesterday
    GROUP BY s.id
) t
WHERE t.today_mean > s.normal_high OR t.today_mean < s.normal_low
ORDER BY abs(t.today_mean - t.yesterday_mean) DESC
LIMIT 10;
```

Three problems, and the third is the worst:

1. `t` is not a name, it is a shrug. Six months later nobody knows what it held.
2. The same `WHERE` logic is written twice — once in the `CASE`, once outside.
   Change one and forget the other and the answer silently becomes wrong.
3. **`s.normal_high` is not in scope.** The subquery grouped by `s.id` and threw
   away everything else, so the outer query has no `normal_high` to compare
   against. The correct query needs it carried out of the subquery, which is a
   change to the inner query *because* of a problem in the outer one. That
   coupling is the actual cost of nesting.

## The CTE version

```sql
WITH bounds AS (
    -- One place for the window, computed once. Stage 01 hard-coded this twice.
    SELECT
        max(ts)                                    AS data_end,
        max(ts) - interval '1 day'                 AS today_start,
        max(ts) - interval '2 days'                AS yesterday_start
    FROM reading
),
daily AS (
    -- One place for "today versus yesterday".
    SELECT
        s.id          AS signal_id,
        s.unit,
        s.normal_low,
        s.normal_high,
        avg(r.value) FILTER (
            WHERE r.ts >= b.today_start
        ) AS today_mean,
        avg(r.value) FILTER (
            WHERE r.ts <  b.today_start
              AND r.ts >= b.yesterday_start
        ) AS yesterday_mean
    FROM reading r
    JOIN signal s   ON s.id = r.signal_id
    CROSS JOIN bounds b
    WHERE r.ts >= b.yesterday_start
    GROUP BY s.id, s.unit, s.normal_low, s.normal_high
)
SELECT
    signal_id,
    unit,
    round(today_mean::numeric, 2)    AS today,
    round(yesterday_mean::numeric, 2) AS yesterday,
    round((today_mean - yesterday_mean)::numeric, 2) AS change,
    CASE
        WHEN today_mean IS NULL      THEN 'no data today'
        WHEN today_mean < normal_low  THEN 'below band'
        WHEN today_mean > normal_high THEN 'above band'
        ELSE 'in band'
    END AS verdict
FROM daily
WHERE today_mean IS NOT NULL
  AND yesterday_mean IS NOT NULL
  AND (today_mean < normal_low OR today_mean > normal_high)
ORDER BY abs(today_mean - yesterday_mean) DESC
LIMIT 10;
```

```
          signal_id           |  unit      | today | yesterday | change |  verdict
------------------------------+------------+-------+-----------+--------+-----------
 SLUDGE:DIG-1:PH              | {pH}       |  6.16 |      6.21 |  -0.05 | below band
 SLUDGE:DIG-1:VFA_ALK_RATIO   | 1          |  0.50 |      0.50 |   0.00 | above band
 AERATION:AHU-1:NH4_OUT       | mg/L       |  7.84 |      7.83 |   0.00 | above band
 SECONDARY:SEC-CL-1:OVERFLOW  | mg/L       | 18.50 |     18.50 |   0.00 | below band
 AERATION:AHU-1:ORCH          | mg/(L.h)   | 28.41 |     28.41 |   0.00 | below band
```

Five rows, and **only one of them has actually moved.** The other four show
`change = 0.00` and are listed because their *level* is out of band, not because
they changed.

That is worth sitting with, because it is a question about what you asked. This
query is *"which signals are out of band"* with a change column attached — not
*"which signals have got worse"*. If you wanted the second, `ORDER BY
abs(change) DESC` would put `SLUDGE:DIG-1:PH` first and drop the other four
entirely. Same data, same CTEs, different question, different answer.

And note `SLUDGE:DIG-1:VFA_ALK_RATIO` reads "above band" while showing `0.50`
today and `0.50` yesterday, because its `normal_high` is below 0.5. That is
correct and it is also a signal whose band somebody should look at.

Two CTEs, each one a sentence:

* `bounds` — *when is today?*
* `daily` — *what did each signal do, on each day?*

Two things worth noticing.

**`bounds` is computed from `max(ts)`, not `now()`.** Same habit as stage 01, now
load-bearing: the whole lesson is a comparison between two windows, and if one of
them is empty the query returns nothing and looks broken.

**`FILTER (WHERE …)` does the two-day split in one pass.** The nested version
needed two `CASE` expressions over the same rows. `FILTER` says *of these rows,
the ones from today* — which is what the question means, and it aggregates both
windows in a single scan.

## CTEs are not just cosmetic: they change the plan

A CTE is read as if it were a subquery, and often is. But Postgres 12+ will
**inline** a CTE that is referenced exactly once and has no side effects, folding
it into the outer query and optimising across the boundary.

```sql
EXPLAIN (ANALYZE, BUFFERS)
WITH bounds AS (SELECT max(ts) AS data_end FROM reading)
SELECT count(*) FROM reading r, bounds b WHERE r.ts >= b.data_end - interval '1 day';
```

Watch for `CTE Scan` in the plan. If it is there, the CTE was materialised — read
into a temporary structure first. That is *worse* for a large result and *better*
when the CTE is expensive and referenced many times:

| | Referenced once | Referenced many times |
|---|---|---|
| `WITH` | usually inlined — good | materialised once, reused — good |
| subquery in `FROM` | inlined — good | **re-executed per reference** — bad |

**So the rule is: if you reference a step more than once, it must be a CTE.** A
subquery pasted in three places is computed three times.

You can force materialisation with `MATERIALIZED`, and the previous version of
this query was accidentally relying on it — which is worth knowing about, because
the two forms are not interchangeable and only one of them is obvious from
reading the query:

<!-- check: skip -->
```sql
WITH expensive AS MATERIALIZED ( … )
SELECT … FROM expensive a JOIN expensive b ON …
```

## `WITH ORDINALITY`, for numbering a generated table

Not needed yet, but it is the answer to "number these rows" and it is two words
away from `generate_series`, which you met in
[01-04](../01-beginner/01-04_time_buckets.md):

<!-- check: skip -->
```sql
SELECT n, generate_series('2026-09-26 06:00+00'::timestamptz,
                          '2026-09-26 18:00+00'::timestamptz,
                          interval '1 hour') AS bucket
FROM generate_series(1, 13) WITH ORDINALITY AS t(n);
```

## Exercises

1. Take the nested version above and count how many times the band comparison
   logic appears. Now do the same for the CTE version. What number would you want
   to see?
2. Write the lesson's query with `bounds` replaced by literal timestamps. Then
   write it with `bounds` replaced by a subquery in the `FROM` referenced twice.
   Which of the three is fastest, and why is the answer not simply "the CTE one"?
3. `EXPLAIN` the CTE version and the nested version. Are the plans the same? If
   they are, what did the CTE actually buy you — and if they are not, which one
   scanned fewer rows?
4. `daily` computes today's mean inside a `FILTER` over a two-day scan. Rewrite it
   as a `GROUP BY` on a derived "which day" column. Which is faster, and what
   decides the answer?
5. The result has five rows and four of them have `change = 0.00`. Change the
   query so that it answers *"which signals have got worse in the last day"*
   rather than *"which signals are out of band"*, and check how the row count
   changes. Then decide which of the two questions your dashboard should be
   asking — and notice that they need different `ORDER BY` clauses, not just a
   different `WHERE`.
6. The `WHERE today_mean IS NOT NULL AND yesterday_mean IS NOT NULL` line is
   there because `NULL` comparisons are never true. Delete it and count the rows.
   What do the extra rows have in common, and what would a reader conclude from
   seeing them?
7. Add a `verdict` of `'rising'` for signals whose change is more than 10 % of
   yesterday's value. Then argue with yourself about whether a percentage is the
   right test for a signal whose normal value is near zero.
