# 02-04 — Gaps: telling a quiet signal from a dead one

**Previous:** [02-03](02-03_window_functions.md) · **[Back to the course](../README.md)**

This is the most practically important lesson in the course, and it is the one
that turns "I have SQL" into "I can tell an operator something they did not
already know".

The problem, in one sentence: **a row exists when the value moved, so the absence
of a row is ambiguous.** No readings means the value did not change — or the
gateway was down — or the instrument died — or the historian was never configured
for that signal. All four look identical in `reading`, and three of them matter.

## The question

> Which signals have stopped reporting, and which are merely quiet?

## Why the obvious answer is wrong

<!-- check: skip -->
```sql
-- Returns nothing, always. Not because the data is fine.
SELECT signal_id, count(*)
FROM reading
WHERE ts >= now() - interval '1 hour'
GROUP BY signal_id
HAVING count(*) < 10;
```

A signal with **no rows at all** in the window does not appear in the result of a
`GROUP BY`. So this query lists signals that are reporting *a little*, and is
silent about the ones that have stopped entirely — which are the only ones you
cared about. This is the same trap as [02-02](02-02_joins.md), seen from the other
side, and it is the single most common way a "find the broken things" query
returns nothing and is believed.

The fix is to start from the list of signals you *expect*, and left-join the
readings onto it.

## The complete query

```sql
WITH bounds AS (
    SELECT max(ts) AS data_end FROM reading
),
-- 1. One row per signal: the most recent reading of each, and how long ago.
last_seen AS (
    SELECT
        s.id            AS signal_id,
        s.unit,
        s.deadband,
        s.sample_ms,
        max(r.ts)       AS last_reading,
        count(r.signal_id) AS total_readings
    FROM signal s
    LEFT JOIN reading r ON r.signal_id = s.id
    GROUP BY s.id, s.unit, s.deadband, s.sample_ms
),
-- 2. How much each signal moved over a recent window. A signal whose value
--    is not moving produces no rows, and that is the whole difficulty.
activity AS (
    SELECT
        signal_id,
        count(*)      AS rows_in_window,
        max(value) - min(value) AS movement
    FROM reading
    WHERE ts >= (SELECT data_end FROM bounds) - interval '2 days'
    GROUP BY signal_id
)
SELECT
    l.signal_id,
    l.unit,
    b.data_end - l.last_reading              AS silence,
    a.rows_in_window,
    round(a.movement::numeric, 3)            AS movement_in_2_days,
    l.total_readings,
    l.sample_ms,
    l.deadband,
    CASE
        WHEN l.last_reading IS NULL
            THEN 'NEVER REPORTED'
        WHEN a.rows_in_window = 0
            THEN 'silent for 2 days: steady, or dead'
        WHEN b.data_end - l.last_reading > interval '6 hours'
            THEN 'SILENT WHILE OTHERS TALK: suspect'
        WHEN a.movement < l.deadband * 3
            THEN 'moving, but barely: quiet is expected'
        ELSE 'reporting normally'
    END AS diagnosis
FROM last_seen l
CROSS JOIN bounds b
LEFT JOIN activity a ON a.signal_id = l.signal_id
ORDER BY
    CASE
        WHEN l.last_reading IS NULL THEN 0
        WHEN b.data_end - l.last_reading > interval '6 hours' THEN 1
        WHEN a.rows_in_window = 0 THEN 2
        ELSE 3
    END,
    silence DESC;
```

The top of the output, and the interesting part is the `total_readings` column:

```

```

**Thirteen signals have `total_readings = 1`.** One, in seven days, and the five
shown above are the worst of them.

That is not a plant that was steady. A digester temperature with a 0.05 °C
deadband over a week produced one row; a rain gauge produced one row. What happened
is this: the deadband publishes the *first* reading of every signal and then
nothing until the value moves. If the value never moves — because the simulated
process holds it constant, or because the signal is only ever computed rather than
measured — you get exactly one row, forever.

**And nothing in the schema objects.** No constraint, no warning, no log line. The
signal is present, the foreign key is satisfied, the row is valid. The deadband did
exactly what it was asked to do, and the consequence is that "reporting normally"
and "reported once in a week and then never again" are indistinguishable from row
counts alone.

This is the honest limit of the deadband design, and it is worth stating plainly
rather than fixing with a heuristic: **a change-detection filter trades
sensitivity for storage, and the price is paid in exactly this place.** The
industry answer is periodic key-value reporting — force a reading every N minutes
regardless of movement — and the reason this project does not do it is that it
would roughly triple the row count, which is a choice with a cost and not a free
improvement. Whether that is the right trade is a judgement about what the data is
for, and `04-expert` returns to it.

The `CASE` is the shape a useful query takes: the numbers are the evidence, the
diagnosis is the judgement, and a reader can disagree with the judgement without
having to re-derive the arithmetic.

## The three tests, and why all three are needed

**Test 1: is the signal silent while others are talking?** This is the strongest
one, and it is the reason the query needs `bounds` at all. A signal that is quiet
at 4am is unremarkable; a signal that goes quiet at 4am *while forty other signals
are reporting* is not. Absolute silence is a signal in itself only in comparison
to the plant's own baseline.

```sql
-- One query: how many signals reported in the last hour, versus the hour before?
SELECT
    count(DISTINCT signal_id) FILTER (
        WHERE ts >= (SELECT max(ts) FROM reading) - interval '1 hour'
    ) AS signals_last_hour,
    count(DISTINCT signal_id) FILTER (
        WHERE ts >= (SELECT max(ts) FROM reading) - interval '2 hours'
      AND ts <  (SELECT max(ts) FROM reading) - interval '1 hour'
    ) AS signals_hour_before
FROM reading;
```

If those two numbers are equal, the gateway is alive and anything silent is quiet.
If the second is much larger, **the gateway stopped for part of the window** and
every signal in the plant is suspect for that period — which is a completely
different alarm, and a much more urgent one.

**Test 2: did the value move?** `max(value) - min(value)` over a window. This
distinguishes "the signal is not writing because nothing is happening" from "the
signal is not writing because the wire is unplugged" — *provided* you compare the
movement against the signal's own deadband. A movement of 0.01 mg/L on a signal
with a 0.02 deadband means nothing happened. A movement of 0.01 on a signal with a
0.001 deadband means the deadband is broken.

That comparison is the one place in this course where you genuinely need the
deadband in the query, and it is worth being clear about why it works here and not
in [02-02](02-02_joins.md): here the deadband is compared against *another
quantity in the same units* — a movement, also in mg/L. Dividing it by a
millisecond would have been nonsense.

**Test 3: has it *ever* been reported?** `max(r.ts) IS NULL` from the `LEFT JOIN`.
The loudest possible diagnosis, `NEVER REPORTED`, is also the easiest to miss,
because a signal that was never configured produces no error anywhere. There is a
test for it in the repo — `tests/test_contract.py` asserts every contract signal
is reachable — and it is worth knowing that the *database* cannot tell you, only
the contract can.

## What a gap is not

One more thing, because it is the mistake everybody makes once.

**A gap is not a zero.** This is the `NULL`-versus-zero lesson from
[00-03](../00-foundations/00-03_quality_is_data.md) applied to time rather than to
a single reading, and it is the same mistake:

<!-- check: skip -->
```sql
-- A gap-filled chart. Every gap is now a zero, and every zero is now a gap.
SELECT bucket, COALESCE(mean_value, 0) AS value
FROM generate_series(...) LEFT JOIN ...;
```

The chart looks continuous. It is also lying, in a way that is worse than the
original gap, because the gap was at least honest about being a gap. Use `NULL`,
and let the chart library break the line. A broken line says *"I do not know"*;
a zero says *"it was zero"*, and those are very different facts about a basin.

## Exercises

1. Run the complete query. How many signals land in each `diagnosis`? For every
   one in `SILENT WHILE OTHERS TALK: suspect`, work out from `deadband` and
   `sample_ms` whether you believe it.
2. Delete the `LEFT JOIN` on `activity` and replace it with an inner join. How many
   signals disappear, and which `diagnosis` values become impossible to produce?
3. Write the gateway-alive test (Test 1) as a single number an operator could look
   at: a green/amber/red. What threshold, and what is the false-alarm rate on a
   normal day?
4. For one signal that is genuinely quiet, find the last time it moved by more than
   `deadband * 3`. Now do the same for one you suspect is dead. What is different
   about the two answers, beyond the number?
5. Add a `NOT EXISTS` variant of the whole query that also catches signals which
   have never been written by *any* source. It should agree with
   `last_reading IS NULL`. Why write it twice?
6. The retention policy deletes `reading` rows after 7 days. What does
   `NEVER REPORTED` mean for a signal first queried 30 days after seeding? What
   would you have to keep in order to answer that question correctly?
